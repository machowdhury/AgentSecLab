Step 6 of 9 · DEFEND  WORLD 2

What control changes?

In the vulnerable run, CTRL-MCP-001 met a known tool that is not in the agent's grant and chose ALLOW because the lab profile is intentionally fail-open. The defended profile enforces the grant.

What changed

The control's profile: fail-open → enforce the grant. The request stays identical.

Why it should matter

The decision, not the model, is what keeps the handler from starting.

What we expect to change

The decision, whether mcp.started appears, and whether pipeline.stopped appears.

There is no switch to flip here: the defended profile is selected by the server. This step explains it; it does not claim the system is now secure.

I understand what changed — continue to RETEST

FRAME 09 Step 9 EXPLAIN / PROVE · desktop AgentSec web app

Step 9 of 9 · EXPLAIN  WORLD 3

Explain it like a security reviewer

Write your own answers somewhere you control. AgentSec does not save them, grade them or treat them as evidence.

1 · What happened?

Under the vulnerable profile, the agent requested an ungranted tool. State what the control decided and whether the handler started.

2 · What evidence supports that?

Name the events and the run.id you read them from.

3 · What does the evidence not prove?

Think: other requests, other tools, completeness of an indexed copy.

4 · What changed after the control?

Compare decision, execution and pipeline.stopped.

5 · What can you safely claim?

“In these two runs, with this request, the control returned ALLOW under the vulnerable profile and the handler started; under the defended profile it returned DENY and the handler did not start.”

Not safe to claim: “the system is secure”, “the attack always works”, “DENY means nothing else ran”.

FRAME 10 Diagram grammar · desktop left-to-right · narrow vertical SVG in Studio image same SVG in web app

Grammar — each element differs by border, glyph and label, not only by colour

Decision branch: ALLOW ━━▶ solid arrow, DENY ╌╌▶ dashed arrow. No green for allow, no red for attack or deny.

LAB-MCP-001 authorization flow — desktop left-to-right (viewBox 1232 × 440)

Typography in the viewBox: primary labels 18–19px, supporting text 15–16px, tags 13px. At a full-width Studio panel the SVG scales up, so rendered text is larger still. The control is the only filled node; nothing is green or red.

Narrow vertical reflow (390)

Rules this frame demonstrates

  • Left-to-right on desktop; the branch drops down so the eye reads one line, then one fork.
  • The PDP is the only filled, double-bordered node. Execution has a heavy teal outline. Stop has a gray bar plus a ■ glyph.
  • ALLOW is a solid arrow; DENY is dashed. Both are labelled in words.
  • Telemetry sits below the boundary, drawn dotted, with dotted arrows in. Splunk receives; it never decides.
  • Narrow screens reflow vertically in a separate SVG. They do not shrink the wide one.

Studio constraint: the Studio image panel cannot switch SVGs by viewport. Studio uses the wide file only. The web app can serve both. Media queries inside one SVG are unverified in a Studio image panel and treated as unsupported until tested.
